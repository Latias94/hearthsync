# WoW Addon Sync Core Review - 2026-04-21

## Summary

This review checks whether the current repository should open a new workstream before the next
fearless-refactor pass.

Judgment: do not create a parallel workstream.
The newly found issues belong to the existing `wow-addon-sync-core` stream because they cut across
provider acquisition, addon mutation semantics, bundle planning boundaries, and the reusable app
contract.

The right move is:

1. keep architecture ownership inside `wow-addon-sync-core`
2. record the findings in this review
3. add an explicit follow-up slice in `todo.md`
4. add a milestone that gates the next refactor sequence

## Why This Should Stay in the Current Core Workstream

- the current findings are not a separate product surface; they are corrections to the existing
  reusable core contract
- the issues span addon provider caching, addon-lock apply semantics, bundle planning behavior, and
  app/runtime boundaries at the same time
- opening another workstream would split the architecture source of truth without reducing
  implementation coupling
- the existing decisions already point in this direction: real-world compatibility and architecture
  hardening stay inside the current core stream rather than creating parallel planning tracks

## Findings

### F1 - Remote source freshness and cache semantics are under-specified

The current addon provider cache can reuse a previously downloaded archive whenever a cache path is
present, without revalidation or mutable-reference awareness.

This is especially risky for:

- `github:owner/repo` without a pinned tag
- direct `http(s)` archive URLs whose content changes over time
- any future provider flow that represents "latest" rather than an immutable artifact

Impact:

- `addon update` can report success while silently reusing an old archive
- mutable remote source references are treated as if they were immutable pins
- GUI-facing "update available" expectations would become unreliable

### F2 - Addon-lock apply is not transaction-complete if post-apply verification fails

`addon lock apply` currently rolls back execution failures, but the operation contract is still not
complete if the post-apply verification phase fails or is cancelled after filesystem mutations have
already succeeded.

Impact:

- the command can return failure after mutation has already happened
- callers cannot cleanly distinguish "apply failed and was rolled back" from
  "apply succeeded but verification failed afterward"
- this weakens the single-operation task contract that future GUI work needs

### F3 - Public plan APIs still perform expensive preview work

The public bundle and external-package plan paths are smaller than before, but they still read
entry bytes and perform rewrite-aware target comparison when an existing target file needs preview
finalization.

Impact:

- default dry-run cost still depends on execution-shaped work
- preview responsiveness for future GUI use remains coupled to archive I/O and rewrite logic
- the planner boundary is improved but not yet purely logical in the strictest sense

### F4 - The stable app boundary still has high forwarding cost

`StableAppServices` and `ExtendedAppServices` now define a credible boundary, but the API shape is
still expensive to evolve because each operation expands into multiple direct/progress/callback
entrypoints and thin forwarding methods.

Impact:

- every new capability multiplies app-surface maintenance cost
- future frontend integration still pays for a broad handwritten façade layer
- more cleanup is still justified before treating the boundary as long-lived and cheap to extend

### F5 - External-helper capability reporting is still placeholder-only

Runtime capability reporting now separates requested policy from active strategy, which is the right
shape, but the actual helper capability contract remains placeholder-only because no concrete
external backend exists and the strategy space still contains only `NativeRust`.

Impact:

- the runtime contract is directionally correct but not yet validated by a real helper path
- future helper integration is still a contract-shaping task, not only an implementation task

### F6 - URL-derived archive naming still has cross-platform edge cases

HTTP archive naming still relies on path-like file-name extraction from the URL string.
This is fragile for URLs with query strings, signed links, or CDN-style download endpoints.

Impact:

- downloaded archive names can be unstable or unsafe on Windows
- author-package and addon source portability is weaker than it appears for real-world URLs

## Recommended Refactor Order

1. fix remote source freshness semantics before promising reliable addon updates
2. make addon-lock apply verification part of a complete operation outcome contract
3. decide whether default plan remains an expensive preview or whether logical planning and
   deep compare should become separate entrypoints
4. continue shrinking forwarding cost at the app boundary only after correctness semantics are
   stable enough to preserve
5. keep external-helper capability evolution in the same core stream as a later bounded slice

## Documentation Follow-up

- `todo.md` should gain a bounded slice for update correctness, transaction completion, and plan-cost clarity
- `milestones.md` should gain a milestone that explicitly gates the next fearless-refactor pass
- no new workstream should be created for these findings
